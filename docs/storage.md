# Хранилище заявок: почему Neon Postgres

Тезисы для README (шаг 8). Что проверено, указано с доказательствами; что взято из документации, с источником.

## Выбор
Заявки хранятся в **Neon Postgres** (бесплатный план, Франкфурт), приложение работает на Render (free web service, Франкфурт).

## Почему не файл и не SQLite
- На Render free локальная файловая система не сохраняется: по документации Render, «локальные файлы теряются при редеплое, перезапуске и засыпании» (render.com/docs/free). Файл или SQLite-база рядом с приложением потеряли бы заявки при первом же деплое или после «засыпания» сервиса.
- Отдельный диск на free-плане Render не поддерживается (там же).
- Заявки нельзя терять: это единственная цель сайта.

## Что даёт Postgres именно здесь
- **Данные живут отдельно от приложения** и переживают деплой, перезапуск и сон сервиса.
- **Дедупликация целиком в базе**, а не в коде приложения: в транзакции берётся замок на номер (`pg_advisory_xact_lock`), затем проверяется свежая запись, затем вставка. Это работает при любом числе экземпляров приложения и при двойном клике.
- Бесплатно, подключается стандартным драйвером `pg`.

## Доказательство дедупликации (ветка `dev`, тест на реальной базе)
10 одновременных запросов с одним и тем же номером, три прогона:

| Вариант | Ответы | Записей в базе |
|---|---|---|
| С замком (как в коде) | 1 × `201`, 9 × `200` (`duplicate`) | **1** (во всех трёх прогонах) |
| Контроль: замок временно отключён | 10 × `201` | **10** (во всех трёх прогонах) |

Контроль показывает, что тест действительно создаёт гонку: без замка дубли возникают сразу. Другие проверки: тот же номер в другом формате (`80297000001` после `+375 29 700-00-01`) считается дублем; через 11 минут (запись состарена в базе) создаётся новая; сразу после неё снова дубль.

## Компромиссы и ограничения
- **Сеть до базы.** Каждый запрос на сохранение идёт по сети в Neon (оба сервиса во Франкфурте).
- **Засыпание базы.** По документации Neon, compute засыпает после 5 минут простоя, пробуждение занимает «несколько сотен миллисекунд». Первая заявка после простоя может отвечать чуть медленнее. Тайм-аут подключения в коде 10 секунд.
- **Одно соединение на запрос, без пула:** пул держал бы мёртвые соединения после засыпания базы; заявок мало. Neon рекомендует `pg` для долгоживущего сервера; свой `@neondatabase/serverless` для этого сценария не рекомендует.
- **Замок через пулированную строку Neon** (PgBouncer): замок уровня транзакции действует в пределах одной транзакции на одном соединении. Подтверждено экспериментом выше (в документации Neon про advisory-замки ничего не сказано).
- **Режим SSL:** драйвер `pg` 8.x выводит предупреждение про `sslmode=require` (сейчас он ведёт себя как `verify-full`; в `pg` 9 поведение изменится). Версия `pg` зафиксирована в диапазоне `^8`.
- **Антиспам:** скрытое поле-ловушка (honeypot); лимита запросов нет.

## Схема
`db/schema.sql` безопасна для повторного запуска (`CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`). На `dev` применена `npm run db:migrate`, на `production` вставляется вручную в SQL Editor Neon.
